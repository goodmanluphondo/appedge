# AppEdge project progress

AppEdge is an internal console for managing clients, hosted applications, custom domains, certificates and routing. Its operational records are stored in Cloudflare D1 through a Worker binding. Microsoft Entra sign-in requires the `AppEdge.Administrator` application role. Privileged infrastructure actions are not connected.

## Work completed

A reusable ChatGPT Project instruction document has been prepared for a self-contained HTML prototype and condensed to fit the 8,000-character limit. It retains the user's language and question handling preferences, canonical demo identities, and the brand content safeguards for approved copy, missing information, functional interface text and metadata. Explanatory repetition and rules outside the prototype's scope were removed so the complete instruction set can be pasted into a ChatGPT Project.

The console follows the "AppEdge Dashboard" design prototype. A dark navy sidebar holds the AppEdge wordmark, seven navigation items (Overview, Clients, Applications, Domains, Routes, Activity, Settings), a red badge on Domains counting hostnames that need attention, and a user menu with Settings and Sign out. On narrow screens the sidebar is replaced by a top bar and a slide-in navigation drawer. Each top-level page shows a header with its title and description, a "Client" scope selector and a "New" menu (Domain, Client, Application). The selected client is kept in a `client` query parameter, carried by the navigation links, and applied in the D1 queries for every page except Activity, so a scoped view can be shared or reloaded. Pages that are not top-level (create forms, setting details, help) keep their own headings.

The Overview shows four tiles (live routes, in progress, needs attention, applications), a "Needs attention" panel, a four-column domain pipeline (Ownership, DNS, SSL, Route), recent activity and an applications list. Because the schema stores ownership, DNS and SSL status separately, the pipeline stage is derived: the first of ownership, DNS and SSL that is not yet verified is the current stage, and a domain past all three is in the Route stage, where it is live if its route is active and otherwise ready. A domain is in error when the status of its current stage is failed. Failure messages and guidance are fixed text per stage because D1 stores no error text. The list pages (Clients, Applications, Domains, Routes, Activity) share one table component with debounced search that writes to a `q` query parameter, and the Domains page has stage and "Needs attention" filter chips in a `filter` parameter. Activity resolves audit resource ids to client names, application names or hostnames so the Resource column is readable. Dates are shown as "12 Oct 2026" and recent events as relative times.

Clicking a domain opens a side drawer controlled by a `domain` query parameter, so it is a server-rendered link rather than client state. It shows the headline status, a progress list for the four stages, DNS records with a copy button, and the domain's audit history. DNS records are read from the stored ownership and certificate record JSON, plus the CNAME target column; the parser tolerates the field names Cloudflare uses. The drawer footer can activate a ready domain's route, deactivate a live one, and remove the domain. These only change AppEdge's own D1 records (the route status, or deleting the route and domain rows) and each writes an audit event, with the removed hostname kept in the event metadata so Activity can still show it. The Routes table lists every domain that has passed all three stages, not just rows in the routes table, so a ready domain appears as Inactive, and its switch performs the same activate or deactivate. A domain with no DNS records stored shows "Waiting for DNS records to be issued" and an empty records message. While a domain loads the drawer shows a skeleton, and it shows "Domain not found" or "Could not load this domain" (with Try again) when the record is missing or D1 fails. Each page also has a loading skeleton and a "Could not load" error panel with Try again.

Creation uses the prototype's modal dialogs, driven by a `modal` query parameter (`client`, `application`, `domain`, `origin`) so they survive a reload. The New menu opens the domain, route, client and application dialogs (the Routes page also has an Add route button), and every "Set origin" button (attention panel, applications list, applications table rows without an origin) opens the origin dialog for that application through an `application` parameter. Adding a domain is two steps: the first validates the hostname and application and returns the DNS records, and the second saves the domain. The ownership token is generated on the server in the first step and sent back in the second, and it is stored in the domain's ownership records together with the CNAME target, so the records shown in the dialog are the same ones the drawer later displays. The CNAME target comes from the required `APPEDGE_EDGE_HOSTNAME` environment variable, which is listed in `.env.example` and inserted into the generated Wrangler configuration as a runtime variable. Publishing a route requires a domain that has passed ownership, DNS and SSL and an application that has an origin; it writes the route as active, points the domain at the chosen application and its client, and the same record is what the gateway reads. If no domain is ready or no application has an origin, the prototype's explanatory dialog appears instead. Applications and routes created in the dialogs get the production environment, because the prototype has no environment field and the schema requires one. All saves write the record and its audit event in one D1 batch. After a save the app navigates to the relevant list (or opens the new domain's drawer) and shows the prototype's "Done" confirmation dialog; creating a domain with no applications, or an application with no clients, shows the prototype's "Could not complete that" dialog instead. The earlier create pages, the Help page and the per-setting detail pages were removed because the prototype contains none of them.

Settings follows the prototype: an Integrations card with a status pill and a Test connection button per integration, and a Roles card. Statuses are real: D1 and Microsoft Entra ID are connected, Cloudflare for SaaS and the gateway are not. Test connection performs a real check (a D1 query, or confirmation that the Entra settings are present) and reports an honest failure for integrations that are not connected. Only the Administrator role is listed, because it is the only role the app enforces.

Parts of the prototype were deliberately left out. The "Gateway healthy" strip with requests per minute, p95 latency and error rate is omitted because no real metrics exist, and showing the prototype's sample numbers would be misleading. The verify ownership, check DNS, check status and retry buttons on pipeline cards, the attention panel and the drawer are not built, because they need live Cloudflare checks that are not connected. The prototype now hides Settings from everyone except an Owner and shows a read-only state for a Viewer; because the app enforces only the Administrator role, Settings is visible to every signed-in administrator and there is no read-only mode. The preview-states switcher, the Owner and Viewer roles and the simulated sign-in belong to the prototype only; the app has a single Administrator role enforced through Microsoft Entra. The dark theme and collapsible sidebar were removed because the prototype has neither. Fonts are Inter, Geist Mono and Syne (for the wordmark), loaded through `next/font`.

The dashboard reads D1 server-side through the Worker binding. Application origins are optional.

The D1 schema models clients, applications, domains, routes, provisioning operations, authentication attempts, sessions and audit events. Domain ownership, DNS, certificate and route states remain separate. Application origins are optional, and route records can be drafted before they are activated. OpenNext supplies the Worker runtime context to server code. Next.js configuration generates the ignored Wrangler file and then initialises OpenNext's local platform proxy with remote bindings disabled, so a clean build can create its configuration before OpenNext reads it and development D1 queries use the local simulator. The local database is selected by `APPEDGE_D1_DATABASE_NAME`, which is also inserted into the generated Wrangler configuration from environment files. Worker names and D1 resource names and IDs are read through a shared required-environment helper in `lib`, then inserted into an ignored generated Wrangler configuration. The helper's runtime implementation uses JavaScript modules so Node.js 20 can load it before starting Next.js; TypeScript callers use a typed library entry point. The committed runtime configuration has no environment-specific resource identifiers. The `.env.example` and local `.env.local` file list Worker, D1 and Microsoft sign-in settings. Next.js development and standard builds generate configuration during Next.js configuration loading, while preview, type generation and local D1 commands use explicit configuration-generation steps before their Wrangler tools run. The local D1 scripts keep schema and seed commands scoped to the local simulator. Cache Components and Partial Prefetching are disabled because this app has no cached data paths and its authenticated dashboards read request-specific D1 data; this follows the Status app's rendering configuration and avoids forcing live database reads through prerender suspense boundaries.

Microsoft sign-in uses an AppEdge-owned OpenID Connect flow with an explicit `/auth/callback` route. `NEXT_PUBLIC_APP_URL` must match the origin serving the app because it determines the OAuth redirect URI and same-origin checks; local Next.js and Worker preview use different ports. A same-origin POST starts sign-in, while a direct GET to the sign-in endpoint returns to the login page. Sign-in attempts store a one-time state hash, nonce and PKCE verifier in D1. The callback consumes the attempt once, verifies the Microsoft ID token signature and its issuer, audience and nonce, then requires the `AppEdge.Administrator` role claim and issues a random opaque session token whose hash is stored in D1 for eight hours. Sign-in and callback requests share a per-source limit of 20 requests in five minutes. Authentication sessions store the user's Entra identifiers, email and display name, without maintaining a separate D1 administrator allowlist. Dashboard session validation awaits Next.js `connection()` inside a Suspense boundary before checking cookies and the current time, keeping session expiry checks at request time. Removing an Entra role assignment blocks future sign-ins; existing sessions remain valid until they expire or are revoked. Query-based sign-in errors also render inside a Suspense boundary so the static login surface remains available while request data resolves. The callback path is explicit application configuration because AppEdge has one configured identity authority and does not need a provider selector in the public URL. Environment variables use explicit app URL, client ID, client secret and tenant ID names. Credentials and application URLs remain outside source control. Entra must define the role and require assignment to the Enterprise application before sign-in can complete.

Local migration and seed commands are provided. Demo client and application records are flagged in D1 and use the canonical demo identity data. Demo applications have no origin URL. The seed does not create domains, access assignments or audit events. No remote D1 resources have been created or changed, and no remote migrations or seed writes have been run.

## Why the data path uses a Worker binding

The application reads D1 through the runtime binding so database access stays server-side and does not require an account token or direct HTTP API connection. Local-only migration and seed commands let the schema and sample data be prepared without writing to a remote database.

The repository now has one baseline migration containing the Entra app role session schema, with no administrators table or follow-up migration. The existing simulator still reflects the earlier schema and was not reset. No migration or seed has been run against remote D1. The Cloudflare adapter and Wrangler are present, while `jose` is declared and locked but not installed in `node_modules`. The configured Wrangler release requires Node.js 22.12 or newer. The default shell Node.js is 20.20.2; the earlier local migration succeeded using installed Node.js 22.22.3. `.nvmrc` selects that compatible version for the project. Microsoft sign-in has not been exercised end to end with an assigned app role.


The redesigned console passes type checking, linting and a production build. Neither it nor the new modals have been viewed or submitted in a browser with real data, because the authenticated pages need a Microsoft sign-in with the Administrator role.
