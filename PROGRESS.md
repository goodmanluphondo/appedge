# AppEdge project progress

AppEdge is an internal console for managing clients, hosted applications, custom domains, certificates and routing. Its operational records are stored in Cloudflare D1 through a Worker binding. Microsoft Entra sign-in requires one of the `AppEdge.Administrator` or `AppEdge.Viewer` application roles. Domain verification and gateway metrics use Cloudflare when its credentials are configured.

## Work completed

A reusable ChatGPT Project instruction document has been prepared for a self-contained HTML prototype and condensed to fit the 8,000-character limit. It retains the user's language and question handling preferences, canonical demo identities, and the brand content safeguards for approved copy, missing information, functional interface text and metadata. Explanatory repetition and rules outside the prototype's scope were removed so the complete instruction set can be pasted into a ChatGPT Project.

The console follows the "AppEdge Dashboard" design prototype. A dark navy sidebar holds the AppEdge wordmark, seven navigation items (Overview, Clients, Applications, Domains, Routes, Activity, Settings), a red badge on Domains counting hostnames that need attention, and a user menu with Settings and Sign out. On narrow screens the sidebar is replaced by a top bar and a slide-in navigation drawer. Each top-level page shows a header with its title and description, a "Client" scope selector and a "New" menu (Domain, Client, Application). The selected client is kept in a `client` query parameter, carried by the navigation links, and applied in the D1 queries for every page except Activity, so a scoped view can be shared or reloaded. Pages that are not top-level (create forms, setting details, help) keep their own headings.

The Overview shows four tiles (live routes, in progress, needs attention, applications), a "Needs attention" panel, a four-column domain pipeline (Ownership, DNS, SSL, Route), recent activity and an applications list. Because the schema stores ownership, DNS and SSL status separately, the pipeline stage is derived: the first of ownership, DNS and SSL that is not yet verified is the current stage, and a domain past all three is in the Route stage, where it is live if its route is active and otherwise ready. A domain is in error when the status of its current stage is failed. Failure messages and guidance are fixed text per stage because D1 stores no error text. The list pages (Clients, Applications, Domains, Routes, Activity) share one table component with debounced search that writes to a `q` query parameter, and the Domains page has stage and "Needs attention" filter chips in a `filter` parameter. Activity resolves audit resource ids to client names, application names or hostnames so the Resource column is readable. Dates are shown as "12 Oct 2026" and recent events as relative times.

Clicking a domain opens a side drawer controlled by a `domain` query parameter, so it is a server-rendered link rather than client state. It shows the headline status, a progress list for the four stages, DNS records with a copy button, and the domain's audit history. DNS records are read from the stored ownership and certificate record JSON, plus the CNAME target column; the parser tolerates the field names Cloudflare uses. The drawer footer can activate a ready domain's route, deactivate a live one, and remove the domain. These only change AppEdge's own D1 records (the route status, or deleting the route and domain rows) and each writes an audit event, with the removed hostname kept in the event metadata so Activity can still show it. The Routes table lists every domain that has passed all three stages, not just rows in the routes table, so a ready domain appears as Inactive, and its switch performs the same activate or deactivate. A domain with no DNS records stored shows "Waiting for DNS records to be issued" and an empty records message. While a domain loads the drawer shows a skeleton, and it shows "Domain not found" or "Could not load this domain" (with Try again) when the record is missing or D1 fails. Each page also has a loading skeleton and a "Could not load" error panel with Try again.

Creation uses the prototype's modal dialogs, driven by a `modal` query parameter (`client`, `application`, `domain`, `origin`) so they survive a reload. The New menu opens the domain, route, client and application dialogs (the Routes page also has an Add route button), and every "Set origin" button (attention panel, applications list, applications table rows without an origin) opens the origin dialog for that application through an `application` parameter. Adding a domain registers it with Cloudflare as a custom hostname as soon as the first step is submitted, because the ownership TXT record can only be shown once Cloudflare has issued it. The second step displays that TXT record and the CNAME to the edge hostname; the domain already exists at that point, so cancelling the second step leaves it in the list (it can be removed from the drawer, which also deletes the Cloudflare custom hostname). If Cloudflare rejects the registration, the new domain row is rolled back and the error is shown in the dialog. The CNAME target comes from the required `APPEDGE_EDGE_HOSTNAME` environment variable. Publishing a route requires a domain that has passed ownership, DNS and SSL and an application that has an origin; it writes the route as active, points the domain at the chosen application and its client; the gateway then picks it up through the resolve endpoint described below. If no domain is ready or no application has an origin, the prototype's explanatory dialog appears instead. Applications and routes created in the dialogs get the production environment, because the prototype has no environment field and the schema requires one. All saves write the record and its audit event in one D1 batch. After a save the app navigates to the relevant list (or opens the new domain's drawer) and shows the prototype's "Done" confirmation dialog; creating a domain with no applications, or an application with no clients, shows the prototype's "Could not complete that" dialog instead. The earlier create pages, the Help page and the per-setting detail pages were removed because the prototype contains none of them.

The gateway resolve API is the only thing the separate AppEdge Gateway Worker (`appedge-gateway-staging` and `appedge-gateway`) needs from this application. The gateway is deployed once and never redeployed when clients, applications or domains change, because every routing decision comes from `GET /api/gateway/resolve?host=<hostname>`. It is machine to machine: it does not use Microsoft Entra sessions or cookies and sets no CORS headers. The caller sends `Authorization: Bearer <token>`, which is compared in constant time (both sides are hashed first, so length does not leak) against the required `GATEWAY_API_TOKEN` setting, a runtime secret listed in `.env.example` and in the generated Worker configuration. A missing or wrong token, or the wrong scheme, always gets the same bare 401. If the setting itself is missing the endpoint answers 500 rather than becoming open. Every response is JSON, sends `Cache-Control: no-store` and an `X-Request-Id`, which echoes the caller's own value when it matches `^[A-Za-z0-9._:-]{1,128}$` and is otherwise generated.

The host is trimmed, lowercased, stripped of one trailing dot and of any port, and must be a valid hostname of at most 253 characters, otherwise the answer is 400 `{"error":"invalid_host"}`. The lookup reads one row (never a list) by joining the domain to its route, the route's application and the domain's client. The answers are: 200 `{"data":{"hostname","client_id","application_id","application_type","environment","origin_url","route_version"}}` only when ownership is verified, DNS is verified, the certificate is active, the route is active, the application is active with a valid origin, the client is active, and the route and application belong to the same application and client as the domain; 404 `{"error":"unknown_host"}` when no domain has that hostname; 409 `{"error":"not_routable","reason":"<code>"}` when the domain exists but cannot route; and 500 `{"error":"internal_error"}` for a genuine database failure, which is logged with the request id. `route_version` is the route's published version and may be null. The reason is the first that applies, in this order: `ownership_pending`, `dns_pending`, `ssl_pending`, `route_missing`, `route_inactive`, `application_inactive`, `no_origin` (no origin, or an unsafe one), `client_archived`, `route_mismatch` (the route serves a different application than the domain, or the application belongs to a different client than the domain). The 409 body carries no other client or application data, and 404 never reveals which client a hostname belongs to. A domain that exists but cannot route gets 409 rather than 404 on purpose, so the gateway can show a "not configured yet" message to the visitor for a hostname the platform knows about, and a "not found" message for one it does not. No audit event is written per resolve, because the gateway calls it on every cache miss, so the handler is strictly read only.

Origin addresses are validated in one shared function, used both when an origin is saved (create application, set origin, publish route) and again when the gateway endpoint reads one, so a bad value can neither be stored nor returned. An origin must be an absolute `https://` URL with a dotted hostname, no credentials, no query, no fragment, no IP literal, and not `localhost` or a name ending in `.local` or `.internal`. The handler logic is pure and takes its database lookup and token as injected functions, which is what lets the tests cover it without a database. `npm test` bundles each `*.test.ts` file with esbuild (already installed as a dependency of Wrangler) and runs them with Node's built-in test runner. The tests cover missing and wrong tokens, host normalisation, unknown hosts, every reason code and the precedence between them, a fully routable domain, cross-client mismatch and unsafe origins.

Settings follows the prototype: an Integrations card with a status pill and a Test connection button per integration, and a Roles card listing Administrator and Viewer. Statuses are computed when the page loads, never fixed. Cloudflare D1 is connected when a query succeeds. Microsoft Entra ID is connected when its three settings are present. Cloudflare for SaaS is connected only when a read-only call listing custom hostnames succeeds with the configured token and zone; missing settings show Not connected, and a rejected token or a Cloudflare failure shows Error. The gateway is connected only when a real request succeeds, made through a Cloudflare service binding named APPEDGE_GATEWAY that points at the gateway Worker named in APPEDGE_GATEWAY_WORKER_NAME. AppEdge calls the binding with GET https://<APPEDGE_EDGE_HOSTNAME>/__appedge/health, because the gateway answers its health path only when the request's host equals its own GATEWAY_HOST (edge.appedge.site). It follows no redirects, waits at most six seconds and requires a 200 whose JSON body has status ok. A missing binding, a binding that throws or times out, any other status, or a 200 that is not the gateway's health body shows Error with the URL that was probed and what came back. There is deliberately no fallback to a public fetch, so a missing binding is visible. A service binding was chosen because a Worker's own fetch to a hostname in its own zone does not trigger Worker routes: AppEdge and the gateway are both in the appedge.site zone and the gateway is attached to edge.appedge.site by a route, so the public request reached the DNS origin and failed with a 522 although the gateway was healthy. The hostname cannot become a Custom Domain because it carries the externally managed Cloudflare for SaaS fallback origin record that customer domains depend on. A service binding is a direct Worker to Worker call that depends on neither hostnames nor zones. The cache request option is not sent because Workers throw when it is set. This replaced an earlier check that only read analytics, which wrongly showed Not connected whenever the Worker name or the analytics permission was missing even though the gateway was serving traffic. The analytics strip on Overview is independent of this check. The card describes the gateway as resolving hostnames through the AppEdge API and proxying requests to their configured application origins. Test connection runs the same check for one integration, reports the specific reason in the dialog and refreshes the pills. Administrators can open Settings and run these checks; Viewers cannot.

The preview-states switcher and the simulated sign-in belong to the prototype only and are not built. The dark theme and collapsible sidebar were removed because the prototype has neither. Fonts are Inter, Geist Mono and Syne (for the wordmark), loaded through `next/font`. Re-testing an origin is not built: no origin health check exists, so a domain never enters an origin error state.

Access control uses two Microsoft Entra app roles carried in the ID token: `AppEdge.Administrator` and `AppEdge.Viewer`. There is deliberately no Owner role. When a token holds several, the highest one wins. The role is stored on the D1 session at sign-in (it is a required column in the single baseline migration), so a role change in Entra applies at the next sign-in and a session can last up to eight hours. A token with none of the three roles is refused as before. Permissions are checked on the server. Viewing needs any role, managing (every create, edit, publish, verify, activate, deactivate and remove action) needs Administrator or above, and Settings, including its integration tests, needs Administrator, so Viewers cannot open it. Every server action checks its permission itself and returns a forbidden message rather than trusting the UI; the Settings page redirects Viewers to the overview. The interface also adapts: Settings is hidden from the navigation, the New menu is replaced by a "Read-only access" badge, and action buttons are removed or, for the route switch and Set origin, show the read-only dialog. These are conveniences only; the server checks are the security boundary.

Domain verification uses Cloudflare for SaaS custom hostnames and keeps five things separate. Ownership is verified when the ownership TXT record issued by Cloudflare is observed in public DNS (looked up through Cloudflare's DNS over HTTPS resolver) or Cloudflare reports the hostname active. DNS is verified when the hostname has a CNAME to the edge hostname, or Cloudflare reports it active; a hostname that resolves to addresses or another target is a failure that names what it resolves to, while no record yet is pending, not a failure. The Cloudflare custom hostname status is stored as reported. The certificate is active only when Cloudflare reports the certificate active, and failure states such as validation timeouts are surfaced with Cloudflare's own message. Routing readiness is a separate step: a route can be activated only when all three have passed and the application has an origin. One check action sits behind Verify ownership, Check DNS, Check status and Retry check. It fetches the hostname from Cloudflare (registering it first if it was never registered), observes DNS, evaluates the result, and only when ownership and DNS both pass but Cloudflare still shows pending does it ask Cloudflare to re-run validation. The result is saved on the domain with Cloudflare's status, a real status message and the check time, and is written to the audit log. Nothing is assumed: not finding a record yet leaves the stage pending with an explanatory message. Duplicate provisioning is prevented in three ways: the hostname is unique in D1 and inserted before Cloudflare is called, every provisioning or check operation first claims a row in the provisioning operations table, and a partial unique index allows only one pending or running operation per domain (stale ones time out after two minutes); registering a hostname Cloudflare already holds adopts the existing one. The Cloudflare calls need `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_ACCOUNT_ID`, which are required secrets in the generated Worker configuration and fail loudly by name when read without a value. Certificate validation uses the HTTP method, so no certificate records are shown.

The gateway metrics strip is a presentational component that only accepts a metrics value, and the data comes through a small source interface with one implementation that reads the gateway Worker's request count, error count, CPU time and per-minute counts from the Cloudflare GraphQL analytics API. Nothing is stored in D1. It needs the gateway Worker name in `APPEDGE_GATEWAY_WORKER_NAME` plus the account ID and API token; when any is missing, or Cloudflare cannot be read, the strip says metrics are unavailable and gives the reason instead of showing numbers. The title says healthy only when requests were seen in the last five minutes with an error rate under five percent, degraded above that, and idle when there were none. Latency is labelled "CPU p99" because the analytics dataset exposes CPU time quantiles; it is not request wall-clock latency, and a different source can supply a different label without changing the component.

The dashboard reads D1 server-side through the Worker binding. Application origins are optional.

The D1 schema models clients, applications, domains, routes, provisioning operations, authentication attempts, sessions and audit events. Domain ownership, DNS, certificate and route states remain separate. Application origins are optional, and route records can be drafted before they are activated. OpenNext supplies the Worker runtime context to server code. Next.js configuration generates the ignored Wrangler file and then initialises OpenNext's local platform proxy with remote bindings disabled, so a clean build can create its configuration before OpenNext reads it and development D1 queries use the local simulator. The local database is selected by `APPEDGE_D1_DATABASE_NAME`, which is also inserted into the generated Wrangler configuration from environment files. Worker names and D1 resource names and IDs are read through a shared required-environment helper in `lib`, then inserted into an ignored generated Wrangler configuration. The helper lives in `require-env` files rather than dot-prefixed `.env` files, because the repository's ignore rule for `.env*` silently excluded the dot-prefixed names and broke the remote build. The helper's runtime implementation uses JavaScript modules so Node.js 20 can load it before starting Next.js; TypeScript callers use a typed library entry point. The committed runtime configuration has no environment-specific resource identifiers. The `.env.example` and local `.env.local` file list Worker, D1 and Microsoft sign-in settings. Next.js development and standard builds generate configuration during Next.js configuration loading, while preview, type generation and local D1 commands use explicit configuration-generation steps before their Wrangler tools run. The local D1 scripts keep schema and seed commands scoped to the local simulator. Cache Components and Partial Prefetching are disabled because this app has no cached data paths and its authenticated dashboards read request-specific D1 data; this follows the Status app's rendering configuration and avoids forcing live database reads through prerender suspense boundaries.

Microsoft sign-in uses an AppEdge-owned OpenID Connect flow with an explicit `/auth/callback` route. `NEXT_PUBLIC_APP_URL` must match the origin serving the app because it determines the OAuth redirect URI and same-origin checks; local Next.js and Worker preview use different ports. A same-origin POST starts sign-in, while a direct GET to the sign-in endpoint returns to the login page. Sign-in attempts store a one-time state hash, nonce and PKCE verifier in D1. The callback consumes the attempt once, verifies the Microsoft ID token signature and its issuer, audience and nonce, then requires one of the two AppEdge role claims, takes the highest, and issues a random opaque session token whose hash is stored in D1 for eight hours. Sign-in and callback requests share a per-source limit of 20 requests in five minutes. Authentication sessions store the user's Entra identifiers, email and display name, without maintaining a separate D1 administrator allowlist. Dashboard session validation awaits Next.js `connection()` inside a Suspense boundary before checking cookies and the current time, keeping session expiry checks at request time. Removing an Entra role assignment blocks future sign-ins; existing sessions remain valid until they expire or are revoked. Query-based sign-in errors also render inside a Suspense boundary so the static login surface remains available while request data resolves. The callback path is explicit application configuration because AppEdge has one configured identity authority and does not need a provider selector in the public URL. Environment variables use explicit app URL, client ID, client secret and tenant ID names. Credentials and application URLs remain outside source control. Entra must define the role and require assignment to the Enterprise application before sign-in can complete.

Local migration and seed commands are provided. Demo client and application records are flagged in D1 and use the canonical demo identity data. Demo applications have no origin URL. The seed does not create domains, access assignments or audit events. No remote D1 resources have been created or changed, and no remote migrations or seed writes have been run.

## Why the data path uses a Worker binding

The application reads D1 through the runtime binding so database access stays server-side and does not require an account token or direct HTTP API connection. Local-only migration and seed commands let the schema and sample data be prepared without writing to a remote database.
